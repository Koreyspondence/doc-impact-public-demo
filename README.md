# Documentation impact demo

This fictional community observatory keeps the dome reservation window in a policy, an operator runbook, and an onboarding guide. Changing the policy alone leaves the other copies stale.

1. Open [the policy change](https://github.com/Koreyspondence/doc-impact-public-demo/pull/1). Show **Files changed**, then expand **Show files to review** in the Documentation Impact comment. The links go to the matching lines.
2. Open [the stacked follow-up](https://github.com/Koreyspondence/doc-impact-public-demo/pull/2). Its **Files changed** shows only the two remaining edits, based on the policy-change branch. The glossary mentions the process without stating a window, and the archive stays untouched.
3. Open [the no-documentation example](https://github.com/Koreyspondence/doc-impact-public-demo/pull/3) to show what the workflow says on an unrelated change.

The checklist is generated by GitHub Actions. The follow-up PR is a staged example, not evidence that Copilot cloud automation ran in this public repository. All PRs are examples; leave them unmerged for the walkthrough.

The [registry](.github/doc-concepts/concepts.json) maps process names to aliases. Add a concept there to begin tracking it. The scanner finds its mentions live instead of storing a separate inventory. See the [Copilot skill](.github/skills/doc-impact-update/SKILL.md) for how a reviewer can use the checklist to prepare a follow-up.
